# Что запросить у заказчика (без доступа к RK и ЮKassa у разработчика)

Разработчик может сделать **сайт, backend, логику заказа и заглушки**. Подключить **боевую оплату и кухню** может только сторона, у которой есть договоры и доступы. Ниже — список, который стоит зафиксировать в договоре / ТЗ **до** финальной интеграции.

---

## 1. Юридическое лицо и деньги

| Что | Зачем |
|-----|--------|
| ИП/ООО, реквизиты, контакт ответственного | Договор ЮKassa, оферта на сайте |
| Решение: **кто получатель платежей** (то же юрлицо на сайте и в ЮKassa) | Иначе webhook и чеки не сойдутся |
| Публичная **оферта** и **политика конфиденциальности** (тексты или согласование) | Обязательно для приёма заказов и оплаты |
| Контакт **поддержки** (телефон, часы) | Сайт, чек, письма |

---

## 2. ЮKassa (оформляет и владеет аккаунтом **заказчик**)

Запросить у заказчика **передать вам** (или техническому админу проекта):

| Данные / действие | Комментарий |
|-------------------|-------------|
| **Shop ID** и **Secret Key** (тест, затем боевые) | В `.env` на сервере, не в репозитории |
| Включён **HTTP-уведомления (webhook)** на URL вида `https://ваш-домен.ru/api/webhooks/yookassa` | Без webhook заказ **не уйдёт на кухню** (по вашей архитектуре) |
| **Return URL** после оплаты: `https://ваш-домен.ru/order/success` | Редirect пользователя |
| Доступ в **личный кабинет ЮKassa** хотя бы одному техническому человеку заказчика | Чтобы настроить webhook, если dev без доступа |
| Режим **тестовых платежей** на этапе приёмки | Заказчик или его бухгалтерия проводит тест-оплату |
| Кто делает **возвраты** при `paid_cart_invalid` (стоп-лист после оплаты) | Процесс, не только разработка |

**Вам не обязательно** иметь личный доступ к ЛК ЮKassa, если заказчик:

1. Создаёт ключи и передаёт их по защищённому каналу.
2. Прописывает webhook URL по вашей инструкции (или даёт вам одноразовый доступ на настройку).

---

## 3. R-Keeper / White Server (оформляет **заказчик** + интегратор RK)

| Что | Зачем |
|-----|--------|
| Договор / **лицензии White Server** (агрегатор, доставка, агент в ресторане) | Без лицензий API не работает |
| Заявка на интеграцию: **integrations@rkeeper.ru** (агрегатор, описание сервиса, тестовый стенд) | Выдают **AggregatorAuthentication** token |
| **objectId** для **каждой точки** (кухни), с которой идёт онлайн-заказ | Выбор точки на сайте → этот id в backend |
| Установлен и настроен **White Server Agent** в каждой точке | Связь облако ↔ RK7 |
| Настройки агента: тип/категория заказа, **доставка vs самовывоз**, стол/режим, таймауты | Иначе заказы падают или не туда |
| **Callback URL** `https://ваш-домен.ru/api/webhooks/rkeeper` доступен из интернета (HTTPS) | Статус заказа с кухни |
| **Тестовая точка** или окно для пробных заказов | Приёмка без реальных клиентов |
| Контакт **интегратора / админа RK** в сети заказчика | Меню, модификаторы, стоп-лист в кассе |

**Токен и objectId** — в `.env` на сервере. Разработчику достаточно **тестового** token + одной тестовой точки для приёмки.

---

## 4. Меню, допы и соответствие id

| Что | Кто |
|-----|-----|
| Финальный **список блюд**, категории, размеры, **допы**, цены (хотя бы Excel / Google Sheet) | Заказчик / бренд-шеф |
| Согласование **стабильных id** (`shawarma-chicken`, `extra-cheese`) — см. [CATALOG-IDS.md](./CATALOG-IDS.md) | Вы заполняете seed, заказчик утверждает |
| После заведения в RK7 — таблица **id сайта → код RK** (`rkeeperCode`) | Делает админ RK по вашему seed, вы проверяете тест-заказом |
| Правило обновления цен: **только в RK / админке** или дублирование в seed | Иначе расхождения и отмены на checkout |

---

## 5. Точки (сеть)

| Поле | Пример |
|------|--------|
| Название, адрес, город | Для выбора на сайте |
| Самовывоз да/нет, доставка да/нет | Флаги на точку |
| Часы работы онлайн-заказа | Как у Chickendener |
| `rkeeper_object_id` | Из лицензирования RK |
| Зона доставки (если есть) | Позже: карта / список улиц — отдельная задача |

---

## 6. Хостинг Beget (аккаунт у **заказчика**)

| Что | Зачем |
|-----|--------|
| Домен, **SSL** | ЮKassa и webhook |
| VPS (рекомендуется) или хостинг с Node | API + webhook, см. [deploy-beget.md](./deploy-beget.md) |
| **SSH** или сотрудник заказчика, кто деплоит | Если у dev нет доступа — CI/инструкция + env |
| PostgreSQL (или доступ к созданной БД) | Заказы, не in-memory |
| `.env` на сервере: `YOOKASSA_*`, `RKEEPER_*`, `DATABASE_URL`, `WEB_ORIGIN` | Секреты |

Минимум для разработчика без доступа к Beget: заказчик создаёт VPS, выдаёт **один deploy** по инструкции или временный SSH на настройку.

## 7. Доступы: что просить «в идеале» vs «минимум»

### Идеально (быстрая приёмка)

- Тестовые ключи ЮKassa + настроенный webhook  
- Тестовый token RK + 1 objectId  
- SSH/staging на поддомене `staging.домен.ru`  
- Контакт админа RK на время приёмки  

### Минимум (вы без доступа к RK и ЮKassa)

| Роль | Делает |
|------|--------|
| **Вы** | Код, staging с заглушками, документация URL webhook, `.env.example`, seed меню |
| **Заказчик** | Регистрация ЮKassa и RK, лицензии, меню в кассе |
| **Техник заказчика / интегратор** | Вбивает env, webhook, прогоняет **1 тестовый заказ** по чек-листу ниже |

---

## 8. Чек-лист приёмки (прогоняет заказчик или интегратор)

1. Меню на сайте совпадает с кассой (названия, допы).  
2. Стоп-лист в RK → позиция недоступна на сайте.  
3. Заказ **самовывоз** с точки A → в RK на точке A.  
4. Заказ **доставка** (если включена) → корректный тип в RK.  
5. Оплата тестом ЮKassa → webhook → **один** заказ в RK (без дубля).  
6. Повтор webhook / двойной клик — **нет второго** заказа в RK.  
7. Callback RK (если настроен) → статус на сайте/в админке обновился.  

---

## 9. Что заложить в договор / смету

- Интеграция RK и ЮKassa — **при наличии** ключей и лицензий; задержки из-за заказчика — отдельный срок.  
- Контент (фото, тексты, меню) предоставляет заказчик.  
- **2–3 итерации** правок вёрстки; смена структуры меню после согласования id — отдельно.  
- Поддержка кассы и эквайринга — не обязанность разработчика, если не оговорено.  
- Один ответственный контакт (**product owner**) с правом утверждать меню и точки.

---

## 10. Одним сообщением заказчику (можно скопировать)

> Для запуска онлайн-заказа с оплатой и кухней R-Keeper нужны:  
> 1) аккаунт ЮKassa на ваше юрлицо, Shop ID и Secret Key, настроенный webhook на наш API;  
> 2) лицензии White Server и token интегратора R-Keeper, objectId каждой точки, установленный агент в ресторанах;  
> 3) меню и допы в кассе, сопоставление с id каталога сайта;  
> 4) домен с SSL и хостинг (VPS), куда мы выложим API и сайт;  
> 5) оферта и контакты поддержки.  
>  
> Разработка сайта и логики заказа возможна без этих доступов; **боевой приём** — после того, как вы или ваш интегратор передадут ключи и прогонят тестовый заказ по чек-листу.

См. также [ORDER-FLOW.md](./ORDER-FLOW.md).
